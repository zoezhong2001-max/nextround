# 面试反馈驱动的迭代

在单场复盘、下一阶段准备或失败后的跨流程总结时使用。固定记录结构，动态调整判断；不把一次面试解释成整个公司的招聘规律。

## 证据分层

1. 面试官/HR 明确反馈：保留原话或准确摘要、来源、日期及反馈所指对象。HR 转述与面试官直接说法分开。
2. 实际提问和追问：记录问题、追问顺序、时间分配及对应能力；“反复追问”可提示关注点，但仍是推断。
3. 候选人回答和结果：记录实际回答、可核对事实、结果与不确定性。未通过不能自动归因于某一道题。
4. JD、团队信息、过往同类样本：仅作背景与先验；公开印象和公司标签权重最低。

每条画像假设都记录：`观察/来源`、`推断的考察意图`、`适用范围`（本面试官/本团队/岗位族/公司）、`置信度`（低/中/高）、`反证或替代解释`、`下一轮如何验证`、`最近验证日期`。只有明确反馈或多个独立样本支持时，才扩大适用范围；新的反证出现时降级或撤回。

## 一次面试后的闭环

1. 冻结准备前的题单与版本，保存原始录音/转写及实际回答，不事后改写“已预测命中”。
2. 在单场 Review 中区分事实、反馈原话、分析推断；回测问题族、追问深度与答案可用性。
3. 在当前 Process 更新“下一轮假设”：面试官可能在验证什么、证据是什么、下一轮哪 3–5 项准备优先级变化、需要问团队确认什么。
4. 同一流程进入下一轮时，先看上一轮 Review、明确反馈与未闭合追问，再结合新轮次/面试官信息调整题单；不能照搬上一轮题单，也不预设两轮面试官关注点相同。
5. 流程结束时做全局复盘：区分个人可控缺口、岗位匹配、流程变量和未知原因；单场形成的可迁移练习写入 Reusable Learnings 时标为“待验证”，跨流程证据满足后再标为“已验证”；仅在该流程成立的判断留在 Process。
6. 下一场面试前选 1–2 个可观察改变（如先给结论、补实验口径），面试后检查是否真正执行、是否改善，而不只检查最终结果。

## 画像与问题预测

画像是“考察假设”，不是对个人的心理推断。可以按业务类型、岗位、团队、轮次和已有追问聚合，但不能仅因公司名称就断言“重数据”或“重产品 sense”。类似印象只作为低置信先验，并至少保留一组反向问题测试迁移能力。

预测优先排序：同流程明确反馈与追问 > 下一轮职责/JD > 候选人证据缺口 > 多个独立同类样本 > 公司印象。输出问题族、考察意图和 2–4 层追问，不预测面试官原句。复盘时用 [question-forecasting.md](question-forecasting.md) 的回测口径更新优先级。

## 晋升与边界

- 本面试官或本团队假设留在当前 Process；涉及可识别人员的记录留在私有库，注意最小化个人信息。
- 多流程反复出现且仍依赖候选人背景的规律进入 Reusable Learnings，附支持样本和反例。
- 只有方法本身可复用、已脱敏、经过验证并获得本次公开发布授权，才进入公开 skill。单家公司或个人画像不发布。
