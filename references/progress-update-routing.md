# 面试进度更新路由

收到笔试、测评、Case、群面、面试安排，或改期、阶段完成、结果、岗位转推、流程关闭或重启等进度信息时读取本文件。目标是让 Process、Current Plan、Review 和下一阶段准备保持一致，同时只更新真正变化的内容。

## 信息可信度

按以下优先级记录流程事实：

1. 公司正式通知、招聘系统状态、邮件或日历邀请。
2. HR、面试官或招聘方的直接消息。
3. 用户对上述消息的准确转述。
4. 根据时间经过、面试体验或对方措辞作出的推测。

前三类可以更新为已确认进度；第四类只能标记“待确认”，不得自行把流程改成通过、未通过或结束。记录结果时保留通知日期和简短来源，不必把完整聊天记录复制进页面。

## 状态含义

内部状态只用于保持页面一致，用户页面显示自然中文：

- `preparing`：已进入一个明确筛选阶段，该阶段尚未开始或提交。
- `waiting-result`：最近一个筛选阶段已经完成或提交，尚无明确结果。
- `advanced-to-next-round`：已明确进入下一阶段，阶段信息待确认或正在准备。
- `offer-received`：已收到 Offer，尚未确认接受或拒绝。
- `closed-pass`：流程成功结束；通常表示 Offer 已接受或用户确认按成功归档。
- `closed-fail`：公司明确通知未通过。
- `closed-withdrawn`：用户主动退出。
- `closed-cancelled`：公司取消岗位、停止招聘或因非候选人结果关闭。

`advanced-to-next-round` 可以持续到下一阶段开始；无需仅因日程已确认改成另一状态。这样 Process 和 Current Plan 不会在“通过”和“安排下一阶段”之间来回跳。

旧页面中的 `interviewing` 视为“流程活跃但阶段未细分”的兼容状态；下一次收到明确事件时迁移到上述状态之一，不为迁移单独改写历史。

`state-check-needed: true` 只表示当前状态需要确认，不替代流程状态。已知面试时间已经过去，而状态仍为 `preparing` 或 `advanced-to-next-round`，且没有更晚的已确认事件时，设置该标记并保留最后一个已确认状态。

## 事件识别、去重与迟到消息

用“公司 + 岗位 + 批次 + 阶段 + 事件类型 + 发生日期”识别一次进度事件：

- 同一事件已经存在于阶段历史时，只补充更可靠的来源或缺失字段，不重复追加。
- 新通知修正旧通知时，保留旧记录并注明被哪条新事实替代；当前区采用较新的已确认事实。
- 迟到消息只补对应阶段的历史和已有 Review，不得把当前状态、当前阶段或下一步退回较早阶段。
- 消息没有明确批次或岗位，且可能匹配多个 Process 时，先让用户确认目标流程。
- 事件日期和通知日期不同，阶段历史使用事件日期，并在来源中保留通知日期。

## 进度事件路由表

| 事件 | Process | Current Plan | Review | Stage Prep / 其他 |
|---|---|---|---|---|
| 首次确认笔试／测评／Case／群面／面试 | 状态设为 `preparing`；写当前阶段、时间或截止日期和下一步；阶段历史去重后追加“当前阶段已安排” | 活跃流程新增或更新一行，写阶段、时间和下一步 | 不创建 | 用户同时要求准备时创建当前 Stage Prep；纯通知只登记状态 |
| 时间、面试官、形式或提交要求变化 | 覆盖最新安排和下一步；阶段历史只在变化影响准备或时间承诺时追加 | 就地更新当前阶段、最新进展、下一步和日期 | 已发生的 Review 不改 | 更新尚未冻结的当前 Stage Prep；不新建重复页面 |
| 笔试／测评／Case 已提交，结果未知 | 状态设为 `waiting-result`；阶段历史追加“已提交，等待结果” | 当前阶段写“已提交，等待结果”，更新下一步 | 不创建 Interview Review | 冻结提交版 Stage Prep；不创建下一阶段准备页，除非用户明确要求提前准备 |
| 互动面试刚结束，结果未知 | 状态设为 `waiting-result`；阶段历史追加“该轮已完成，等待结果”；下一步写复盘及等待节点 | 当前阶段写“面试结束，等待结果”，更新下一步 | 有逐字稿、录音或可靠回忆时创建该轮 Review | 冻结当前 Stage Prep；不创建正式下一阶段准备页，除非用户明确要求提前准备 |
| 明确进入下一阶段 | 若不是迟到消息，状态设为 `advanced-to-next-round`、当前阶段改为下一节点并更新下一步；阶段历史对上一阶段结果去重后追加 | 若不是迟到消息，原行就地更新为“已进入下一阶段”，写安排或待确认项 | 已有上一轮 Review 时补结果和通知来源，不重写实际问答；没有 Review 时不新建空页 | 冻结上一阶段准备；已有可执行准备内容或用户同时要求准备时，创建独立的下一阶段 Stage Prep；纯状态更新不创建空页 |
| 下一阶段时间或形式随后确认 | 保持 `advanced-to-next-round`；覆盖阶段安排、下一步和相关岗位事实 | 就地补齐时间、形式和准备动作 | 上轮 Review 不改 | 已有下一阶段 Stage Prep 时增量更新；用户开始准备或信息已足以形成实质内容时创建 |
| 明确未通过 | 状态设为 `closed-fail`；阶段历史对结果去重后追加；填写结案摘要和已知原因边界 | 从活跃流程移到“最近结束” | 已有最后一轮 Review 时补“后续流程结果”和明确反馈；没有互动面试材料时不新建空 Review | 不创建下一阶段准备；只有用户要求复盘或已有分析材料时才修 Experience Card / Reusable Learning |
| 用户主动退出 | 状态设为 `closed-withdrawn`；记录退出日期和用户确认的决策依据 | 移到“最近结束” | 有已完成面试时可补流程结果，不把退出解释为面试失败 | 取消后续准备；不删除历史材料 |
| 公司取消岗位或停止招聘 | 状态设为 `closed-cancelled`；记录通知与非候选人原因 | 移到“最近结束”，结果写“岗位取消 / 停止招聘” | 已有 Review 只补流程结果，不归因于表现 | 取消后续准备；不生成失败复盘结论 |
| 收到 Offer | 状态设为 `offer-received`；记录 Offer 日期、回复期限、待确认信息和下一步 | 活跃流程保留，阶段更新为“已收到 Offer” | 最后一轮 Review 可补结果，不承担决策记录 | 不要求专门 Offer 页面；需要比较时使用现有 Process 与 Current Plan |
| 接受 Offer 或确认成功归档 | 状态设为 `closed-pass`；完成结案摘要和选择依据 | 移到“最近结束” | 已有最后一轮 Review 时只补后续流程结果 | 不再创建面试准备页 |
| 岗位转推 | 保留原岗位分支的当前阶段和结果；在同一父流程下创建新岗位分支 | 原流程写转推结果，新岗位作为独立活跃项或清晰的子项 | 原岗位 Review 只补“发生转推” | 为新岗位重新校准事实并创建对应 Stage Prep；不直接复用原岗位题单 |
| 已关闭流程重新联系 | 同一批次则追加“重新激活”并切换到适用状态；新批次新建 Process | 恢复到活跃流程，写新的时间与下一步 | 历史 Review 不改 | 复用材料前重新确认 JD、岗位范围和经历口径 |
| 仅有推测、超过预计反馈时间 | 保持原状态；增加状态待确认和最后一次已知事实 | 下一步写“向招聘方确认”，不移动到最近结束 | 不补结果 | 不因沉默创建下一阶段准备或失败归档 |

## “一面通过”的标准更新

收到可信的一面通过通知后，一次更新应形成以下结果：

1. **一面 Review：** 已存在时只补“本轮结果：通过并进入下一轮”、通知来源和新的下一步；实际问题、实际回答和原诊断保持不变。Review 不存在时不因一条通过通知新建空页。
2. **Process 当前区：** 当前状态改为“已进入下一阶段”，当前阶段改为二面，下一步写清二面时间或待确认项，最近状态确认写通知日期。
3. **Process 阶段历史：** 尚未记录该事件时新增一行“一面｜通过｜一面准备｜一面复盘｜准备二面”；重复通知不追加第二行。
4. **Process 下一阶段重点与材料：** 更新已有依据支持的二面准备重点；创建二面 Stage Prep 时再补链接。
5. **Current Plan：** 同一岗位原行就地改为“已进入二面”，更新最新进展、下一步和最近更新；不得新增第二条重复流程。
6. **二面 Stage Prep：** 有可执行准备内容或用户同时要求准备时单独新建。没有二面面试官、时间或形式时，只写真正影响准备的待确认项，不用占位内容补齐模板。

仅收到“通过”而用户没有要求立即准备下一阶段时，仍需创建最小二面准备页吗？默认不机械创建空页：先在 Process 与 Current Plan 完成状态闭环；当已有二轮信息或本次任务包含下一阶段准备时再创建正式 Stage Prep。

如果“一面通过”在二面已经结束后才补录，只更新一面 Review 和 Process 阶段历史；当前状态、当前阶段、Current Plan 下一步仍以二面后的较新事件为准。

## 原子更新与失败处理

将一次进度变化视为一个一致性更新：

1. 写入前读取最新 Process、Current Plan、对应 Review 和尚未冻结的 Stage Prep。
2. 先识别唯一事件、结果来源、发生日期、通知日期、是否已记录，以及它是否晚于当前已确认事件。
3. 更新对应 Review 的结果，再更新 Process 当前区与阶段历史，最后更新 Current Plan；需要时创建或修改下一阶段 Stage Prep。
4. 写入后重新读取这些页面，核对公司、岗位、批次、当前阶段、结果、下一步和链接一致。
5. 任一页面更新失败时，不声称“已全部同步”；保留成功写入部分，明确列出未完成页面和应写值，下一次先修复一致性。

不得为了实现“原子性”回滚或覆盖用户刚刚修改的内容。遇到并发修改时停止该页面写入，返回冲突和最小补丁建议。

## 禁止动作

- 不把同一结果追加为 Current Plan 的新段落、Process 页尾备注和准备页状态说明，造成三份重复正文。
- 不因面试感觉良好、HR 使用积极措辞或长时间无回复推断通过或未通过。
- 不把岗位取消写成用户主动退出，也不把主动退出写成面试失败。
- 不在下一阶段准备页中改写上一轮实际表现；上一轮事实留在 Review。
- 不删除或覆盖已冻结的旧轮次准备和复盘。
