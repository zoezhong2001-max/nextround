# Agent Memory 机制设计

NextRound 是一个长期陪伴单一用户的求职 Agent 工作台。这类系统的核心难题不是「记住更多」，而是：**在 Agent 持续生成内容、用户持续人工修正的协作中，保证记忆可信、可追溯、不过期误用**。本文记录当前版本的机制设计与背后的取舍。

## 设计目标

1. 用户的修正永远优先于 Agent 的生成物，且不会因为 Agent 重新生成而丢失。
2. 任何一条「事实」都能回答：来源是什么、核实状态如何、何时被谁改过。
3. Agent 复用历史成果前，能判断它是否已经过期。
4. 原始证据（面试逐字稿、实际问答）不可被任何后续分析改写。

## 总体结构：基础文档 + 编辑日志叠加

```
┌────────────────────────────────────────────────┐
│ 读取视图 readRebuild(store)                     │
│  = 基础文档 workbenchDocument                   │
│  + 按序重放 rebuildEdits（人工编辑日志）          │
│  → 返回当前内容 + editRevision + editHistory    │
└────────────────────────────────────────────────┘
         ▲ 写入                   ▲ 写入
         │                        │
  Agent 生成/迁移基础内容      用户在工作台直接编辑
  （事务写入 SQLite）          （追加编辑日志，不改基础文档）
```

- **正式存储唯一**：个人资料、经历、复盘、问题族等全部保存在私有 SQLite 的 `workbenchDocument` 中。历史导入文件（如 dossier 快照）只是迁移来源，不作为第二套日常数据，避免「两个真相」。
- **人工编辑是附加日志，不是原地改写**：用户在工作台的每次修改追加为一条 `{ ref, before, after, at, author: "user" }` 记录进 `rebuildEdits`。读取时按序叠加到基础文档上。因此 Agent 重新生成基础内容时，人工修改天然保留、天然优先。
- **编辑带 diff**：每条记录保存 before/after，工作台可展示修改历史，支持审计与回滚。

## 可编辑性白名单：区分「证据」与「派生物」

不是所有内容都允许同样的修改。写入路径用一张字段白名单（`fields`）强制区分：

| 可编辑（分析、建议、示范、更正备注） | 不可通过内容编辑改写（证据与流程事实） |
|---|---|
| 记忆文本与备注、档案事实值、经历说明与时间、复盘结论与行动、逐题诊断与更正、问题组建议、问题族摘要 | 原始问题与实际回答、来源引用、流程结果状态 |

这条边界同时约束人和 Agent：建议可以被持续修订，但没有人能把「后来的建议」改写成「当时的事实」。

## 过期检测：revision 比对

- `editRevision = sha256(基础文档 + 编辑日志)`，每次读取实时计算。
- 用户编辑走乐观并发：提交时必须携带当前 revision，不匹配返回 409，防止覆盖他人的新修改（单用户场景下主要是防止「开着旧页面保存」）。
- Agent 侧对称设计：派生产物（例如一份基于记忆生成的准备稿）记录其生成时的 `memoryRevision`；**回答或复用前与当前 `editRevision` 比对，不一致则重新核对依赖，而不是沉默地复用旧 prose**。

## 事实分级与来源

记忆条目不假设「写下来的就是真的」。档案事实和上下文记忆都带：

- `sources`：来源记录 ID 列表（材料、逐字稿、用户纠正记录）。
- `status`：核实状态分级，例如「材料记载」「本人确认 / 本人明确表达」「分析与建议 · 待验证」。
- 历史面试中的原话只证明「当时这样表达」，不自动升级为已核实事实；跨场观察明确标注「非人格定论」。

## Agent 的最小上下文读取

Agent 不默认加载整套资料库，而是通过记忆检索接口按需读取：

```
memoryContext(store, { q, experienceId, applicationId, evidenceId })
```

- `q`：关键词检索，命中数 × 10 计分，与当前岗位关联的经历加权 +5，最多返回 12 条。
- `experienceId` / `applicationId`：按经历或岗位收窄。
- `evidenceId`：精确取回某一道历史问答的完整证据（写复盘示范时引用）。
- 未命中时返回显式提示：「关键词未命中不代表资料不存在」，防止 Agent 把检索空洞当成事实空洞并向用户重复提问。
- 响应携带当前 `revision`，供下游做过期判断。

## 为什么不用向量检索

当前是单用户、单机、语料规模有限的场景：全量记忆条目在百级，关键词 + 经历关联加权的延迟与可解释性都更好，且没有引入 embedding 服务的运维与隐私成本。代码中对此留了显式注释：只有当实测延迟成为问题时才加文本索引。这是一个有意的「不过度设计」决策，而不是功能缺失。

## 边界与约束

- 私有数据整体保存在被 git 忽略的运行目录（`.local-data/`），公开仓库不含任何个人记录。
- Agent 不能通过人工编辑接口写入——那会把自己的断言归因给用户。Agent 的修改以草稿形式存在，由用户确认后才成为事实。
- 编辑日志目前保存在单条 setting 记录中（单用户日志，读取成本可接受）；若将来量变大，再迁移为索引行。
