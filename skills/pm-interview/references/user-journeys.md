# 用户旅程与组合工作流

在每次使用时先识别用户当前发生的求职事件，再组合准备、复盘、经历深挖、状态更新和归档能力。一次任务可以产生多份独立文档；不把不同轮次或用途的内容合并成一页。

“完成整条链路”表示把本次事件中确实发生的工作闭环，不表示机械生成所有模板。没有新事实、分析或行动需要承载的页面不创建，空板块不输出。

## 纯进度通知

用户只告知进入笔试、测评、Case、群面、面试、改期、通过、未通过、岗位取消或转推，且没有提交材料或要求复盘/准备时，只按 `progress-update-routing.md` 更新状态和必要链接。不要因为该事件可能属于更长旅程，就自动生成 Review、经历修复或下一阶段准备。

## 0. 首次使用与最小建档

首先定位唯一的 PM Interview Hub。没有 Hub 时，只在获得授权后按 `assets/templates/hub.md` 建立最小结构。

### 用户已经进入明确招聘流程

冷启动不得阻断当前面试准备：

1. 优先读取用户提供的最新简历、JD 和当前筛选阶段、时间或截止日期。
2. 只提取当前岗位会用到的个人事实、数字、职责边界和两至三段候选经历，建立最小 Profile。
3. 创建当前 Process 和 Current Plan 记录。
4. 立即继续“已进入首个筛选阶段”旅程；不要求用户先完成所有经历卡、通用自我介绍或全量事实盘点。
5. 准备中出现的关键事实缺口标为待核实，只追问会影响当前阶段产出的项目。

### 用户尚未约面

仅根据已有材料建立最小 Profile、Current Plan 和经历索引。不主动执行职业方向探索、岗位筛选、JD 投递建议或大量通用题库建设；等用户带来明确面试或单项请求。

### 完成条件

- Profile 足以支撑当前任务，高风险事实已确认或标出待核实。
- Current Plan 反映当前阶段；有面试时已登记当前流程。
- 已进入招聘流程时已继续完成相应准备，而不是停在建档。

## 1. 已进入首个筛选阶段

识别信号：用户已经通过简历筛选，或收到在线笔试、测评、Case、群面、Assessment Center、首轮面试等明确安排，并带来题目、通知、JD 或岗位背景。

### 工作链路

1. 查找同一“公司 + 岗位 + 批次”的 Process；不存在时创建。
2. 读取 Profile、JD 和当前岗位真正会用到的 Experience Cards。
3. 提炼岗位范围、当前阶段的考察目标、候选人证据和高风险缺口。
4. 如果核心经历无法支撑当前任务，先做最小必要的经历修复，再生成该阶段的 Stage Prep。
5. 根据阶段类型组织产出：笔试开放题保存可提交答案；Case 保存问题拆解与成品；群面或 Assessment Center 保存角色策略和练习；面试保存题单、故事与反问。
6. 根据用户需求进行模拟；模拟是本旅程的可选环节，不是另一条流程。
7. 更新 Process 和 Current Plan，链接准备页与简历版本。

### 完成条件

- Process 的岗位事实、当前阶段、下一步和材料链接已更新。
- Stage Prep 能直接支持当前筛选阶段，且只包含有证据的事实、答案或交付物。
- 当前阶段必须补齐的事实、答案和行动已明确。

## 2. 一个筛选阶段结束，流程继续或结果待定

识别信号：用户已经提交笔试、测评或 Case，或完成一轮互动面试、群面、Assessment Center，并且流程尚未结束。

### 共同链路

1. 读取当前 Process、当阶段 Stage Prep 和实际使用的 Experience Cards；互动面试还读取逐字稿或可靠回忆。
2. 互动面试按 `review-and-archive.md` 完成本轮 Review，校准岗位范围、真实问题、答案质量和明确反馈。纯笔试、测评或 Case 只冻结提交版本并更新 Process；除非用户明确要求复盘，否则不创建 Interview Review。
3. 有真实互动问题时与本阶段准备回测，更新问题族优先级。
4. 对被连续追问、答案冲突或造成误解的核心经历，在同一任务中做必要的 Experience Card 修复。
5. 更新 Process 的岗位事实、阶段历史、当前状态和下一步，并就地更新 Current Plan 对应行。

### 已明确进入下一阶段

继续读取下一阶段的形式、时间、面试官或交付要求。有可执行准备内容或用户同时要求准备时，在同一任务中生成独立的下一阶段 Stage Prep；如果本次只是状态通知且关键信息不足，先完成状态闭环，不创建空页。不把本轮 Review 与下一阶段准备合并为一篇文档。

### 结果待定

互动面试立即完成 Review 和必要的经历修复，并把流程标为等待结果。纯笔试、测评或 Case 只冻结提交版并更新状态。可给出简短的提前准备建议，但不创建正式下一阶段准备页，除非用户已经获得下一阶段或明确要求提前准备。

### 岗位转推

保留原岗位分支的轮次事实和结果，在同一父流程下建立新岗位分支。可继承公司级背景，但必须重新校准岗位事实、经历匹配和问题族；不把原岗位反馈当成新岗位的确定事实。

### 完成条件

- 发生互动面试时，本轮 Review 已完成且原始问答可追溯；纯书面阶段的提交版本已冻结。
- 对后续有影响的经历缺口已修复或明确标为待补。
- Process 与 Current Plan 状态一致。
- 进入下一阶段且已有可执行准备内容时，已生成独立的 Stage Prep；否则下一步明确为补齐信息或开始准备。

## 3. 流程未通过、主动退出或被取消

1. 完成最后一轮 Review；没有录音或逐字稿时使用用户可确认的回忆，不补写问题顺序或表达听感。
2. 把可控缺口、岗位匹配、流程变量和未知原因分开；不仅凭未通过推断某道题导致结果。
3. 修复对后续面试仍有价值的 Experience Cards，将跨流程仍成立的规律写入 Reusable Learnings。
4. 更新 Process 结案摘要和最终状态；把 Current Plan 中该流程从活跃表移至最近结束。
5. 不生成下一阶段准备。岗位取消或用户主动退出时，不把结果归因于候选人表现。

## 4. Offer 与选择

把已确认信息、个人偏好、待确认问题和风险分开。可以按团队/岗位范围、成长机会、业务方向、工作地点、时间与其他用户明确在意的维度比较；不替用户做决定，不把未核实信息当成确定事实。

- 接受：关闭该 Process，记录选择依据，更新 Current Plan。
- 拒绝：按主动退出关闭，记录决策依据。
- 等待其他流程：保持为活跃决策项，明确截止日期和待询问信息。

## 5. 求职季结束

1. 核对 Current Plan 中所有活跃流程，只在用户确认后关闭状态不明的项目。
2. 汇总有效定位、高频问题族、反复发生的经历/表达缺口和低价值准备投入；不只用通过率评价。
3. 更新 Profile 和核心 Experience Cards，合并重复的 Reusable Learnings，归档当期 Current Plan 和已结束 Processes。
4. 如果用户将继续下一求职周期，新建对应时期的 Current Plan，不在旧计划末尾继续追加。

## 6. 面试触发的经历修复

这是可独立调用、也可嵌入第 2 或第 3 旅程的横向工作流。

1. 定位 Review 中对应的问题组、真实追问、实际回答和面试官反应。
2. 对照现有 Experience Card，区分事实缺口、思考缺口和表达缺口。
3. 只就无法从已有材料确认、且会影响后续答案的事实向用户追问。
4. 更新项目树、职责边界、实现机制、指标字典、关键判断和易误解表述。
5. 重建 30 秒、90 秒和三层以上追问答案，且共享同一事实模型。
6. 只在简历事实不准确、职责边界误导、指标口径需修正，或用户明确要求时，才生成新简历版本。

### 完成条件

- 真实面试追问已映射到 Experience Card。
- 项目树、职责、机制、指标与多层回答一致。
- “当时做法”、“面试实际回答”和“复盘后方案”没有混淆。

## 7. 明确的单项任务

用户可以明确只要模拟面试、修改自我介绍、优化某条简历、深挖某段经历或练习某道题。此时尊重用户设定的范围，只加载必需材料；不强制执行完整用户旅程。

## 共通例外与停止条件

- 无录音或逐字稿时仍可复盘，但必须区分原话、准确回忆和模糊回忆，不分析无证据的语速、停顿或语气。
- 用户首次使用时已处于笔试、Case、群面、二面、等待结果或 Offer 阶段，先建立最小 Profile 和当前 Process，然后直接接入对应旅程；不强制回放全部旧过程。
- 多流程并行时，Current Plan 统一排序，每个 Process 保持独立。单家公司的面试假设不能直接写入其他流程。
- 旧流程重新联系时，同一批次可重新激活；新批次建立新 Process。继承旧材料前先重新确认岗位范围、时间和经历口径。
- 缺少的用户信息只有在会改变当前旅程分支或使产出无法可靠完成时才询问；其他情况使用已有证据继续，并标明待核实。
